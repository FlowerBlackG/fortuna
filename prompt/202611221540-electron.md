# Fortuna: Implement a Self-Contained Electron Desktop Application with Built-in and Remote Backend Modes

## 0. Repository and objective

**Repository:** https://github.com/FlowerBlackG/fortuna  
**Base branch:** `develop`

**Target platforms:**
- Windows 11 x64
- macOS 26+ ARM64 (Apple Silicon)

**Existing technology stack:**
- Python 3.14+
- Flask
- Waitress
- SQLite
- Argon2 authentication
- React 19
- TypeScript
- Vite+
- TDesign

The existing application follows a browser/server architecture. The Python backend runs independently, and the React frontend communicates with it over HTTP.

Implement a self-contained Electron desktop distribution while preserving the existing browser/server deployment and functionality.

The Electron application must:

1. Bundle the Python backend, Python runtime, dependencies, frontend, and Electron runtime.
2. Require no globally installed Python, Node.js, or other development environment.
3. Run a private, localhost-only Python backend.
4. Store SQLite data persistently in a location accessible to the user.
5. Support an automatically authenticated built-in account.
6. Skip backend configuration and login when using the built-in backend.
7. Allow Electron users to switch between the built-in backend and an externally deployed Fortuna backend.
8. Preserve the existing login, registration, configuration, and logout workflows when using a remote backend.
9. Keep the original web build strictly remote-only.
10. Remain compatible with the existing API, database structure, business logic, and deployment workflows.

**This must be implemented as production-quality functionality, not a demonstration or prototype.**

Read the current repository carefully before modifying anything. Verify all referenced paths, APIs, models, functions, and configuration structures against the actual `develop` branch. Adapt the implementation to the real code rather than blindly following illustrative snippets.

Avoid unrelated rewrites.

# 1. Core architectural principles

Fortuna will support two distribution types and two connection modes.

## 1.1 Distribution types

### Web/server distribution

Preserve the current architecture:

```text
Browser
   |
   | HTTP/HTTPS
   v
Fortuna Python Server
   |
   v
SQLite Database
```

The existing web/server distribution must continue to work normally.

The React frontend may be deployed separately from the Python backend.

### Electron distribution

Implement:

```text
Electron Application
|
+-- React UI
|      |
|      v
|   Electron Preload API
|      |
|      v
+-- Electron Main Process
       |
       +-- Built-in mode
       |      |
       |      v
       |   Bundled Python Backend
       |      |
       |      v
       |   Local SQLite Database
       |
       +-- Remote mode
              |
              v
           External Fortuna Server
              |
              v
           Remote Database
```

Electron main owns the backend connection mode, the local Python process, and the private authentication credentials.

React must not have direct access to operating-system APIs or the private embedded backend authentication secret.

## 1.2 Connection modes

The Electron application supports:

- `builtin`
- `remote`

The normal web build supports only `remote`.

The selected Electron connection mode must persist across restarts.

On the first launch of a fresh Electron installation, default to `builtin`.

Connection-mode switching must not automatically migrate, synchronize, copy, merge, or delete data.

The built-in and remote databases are independent.

# 4. Separate application environment from runtime mode

This is a critical security requirement.

Introduce two independent concepts:

## 4.1 Application environment

Continue supporting the existing environment values:

```text
development
staging
production
```

The environment controls the existing behavior, such as development diagnostics and production-safe configuration.

## 4.2 Backend runtime mode

Introduce an internal runtime mode:

```text
server
embedded
```

The meaning is:

| Environment | Runtime mode | Intended purpose |
|---|---|---|
| development | server | Normal development |
| staging | server | Normal staging |
| production | server | Normal deployed server |
| production | embedded | Electron-managed backend |

Other environment/runtime combinations involving `embedded` must be rejected.

**The embedded backend must always run with `environment = production`.**

It must never run Flask debugging, development reloading, or an exposed debug server.

## 4.3 Secure activation of embedded mode

Embedded mode must not be enabled automatically by:

- An environment variable alone.
- A configuration JSON property alone.
- An HTTP header.
- An API request.
- A frontend parameter.
- The existence of an SQLite database.
- The existence of a built-in account.
- A particular hostname or port.
- A request originating from localhost.

Implement a dedicated internal desktop launcher or explicit internal startup entry point.

For example, conceptually:

```text
Normal server entry point
    -> create_app(runtime_mode="server")

Dedicated Electron backend entry point
    -> create_app(runtime_mode="embedded")
```

The dedicated desktop launcher should be packaged for Electron.

The independently deployed server should continue using the normal server entry point.

The server mode must be the default, and enabling embedded behavior through ordinary server configuration must not be possible.

An internal command-line argument may be used within the dedicated desktop launch path, but it must not be treated as proof of Electron's identity. The mandatory authentication secret provides the actual protection for requests.

In embedded mode, reject startup unless all safety requirements are satisfied:

1. Environment is production.
2. Listening address is exactly IPv4 loopback, `127.0.0.1`.
3. The embedded authentication secret is present and valid.
4. Debug mode and reloading are disabled.
5. The selected configuration is valid.
6. Database storage is writable.
7. The backend can initialize and resolve its persistent built-in account.

Never automatically fall back to normal server behavior when embedded initialization fails.

Likewise, normal server mode must never automatically fall back to embedded authentication.

# 6. Embedded backend lifecycle

Electron main must manage the Python process.

## 6.1 Startup

When the user activates built-in mode:

1. Resolve the persistent application-data directory.
2. Generate or load the embedded backend's configuration.
3. Generate a new cryptographically random 256-bit authentication secret.
4. Start the bundled Python executable.
5. Pass the secret privately to the child process.
6. Wait for verified backend readiness.
7. Obtain the dynamically assigned listening port.
8. Initialize the Electron API transport.
9. Allow the frontend to enter the built-in workspace.

Do not display the workspace before the embedded backend is ready.

## 6.2 Local network binding

Bind the embedded backend exclusively to:

```text
127.0.0.1
```

Use an automatically assigned port:

```text
port = 0
```

Obtain the actual assigned port after the listening socket has been successfully created.

Never use a hardcoded port such as 5000.

Never allow an embedded process to listen on:

```text
0.0.0.0
::
public network interfaces
```

Use the existing Waitress server implementation.

Investigate a programmatic Waitress startup using `create_server()` or an equivalent mechanism that provides the effective assigned port before the server starts accepting application requests.

## 6.3 Readiness protocol

Implement a structured readiness message between Python and Electron.

For example:

```json
{
  "type": "ready",
  "host": "127.0.0.1",
  "port": 51234
}
```

The port above is illustrative.

Electron must distinguish readiness messages from logs.

Ensure Electron does not confuse output from dependencies with the readiness protocol.

Prefer a dedicated private startup IPC channel if practical. A carefully defined stdout protocol is acceptable.

Do not include authentication secrets in readiness messages or logs.

## 6.4 Process handling

Implement:

- Startup timeout.
- Meaningful startup failure messages.
- stderr/stdout diagnostics.
- Unexpected process termination handling.
- Graceful shutdown.
- Forced termination as a fallback.
- Cleanup on Electron exit.
- Prevention of orphaned backend processes.
- Electron single-instance locking.
- Safe handling of rapid mode switching.
- Prevention of multiple embedded backends accidentally operating on the same database.

Prefer to stop the embedded backend when switching to Remote mode, unless there is a clear technical reason to keep it running.

When switching back to Built-in, start it again as necessary.

The account identity and SQLite data must remain stable regardless of process restarts.

# 7. Built-in account: exact implementation design

This section is mandatory.

**The built-in account must be a real, persistent database account, not a fake frontend identity or an unconditional authentication bypass.**

## 7.1 Account fields

Use the following design:

| Field | Value |
|---|---|
| Username | `__fortuna_builtin__` |
| Display name | `Local User`, if the current model supports display names |
| User ID | Generated using Fortuna's existing `str(uuid.uuid7())` mechanism |
| Password | Randomly generated, not user-provided |
| Password storage | Existing Argon2 password hash |
| Account identification | Dedicated persistent SQLite metadata marker |
| Login method | Private Electron-to-Python authentication, not username/password |

Do not hardcode the user ID.

Do not assume it is `1`.

Do not create a new user ID on every application launch.

The built-in user ID must remain stable even after upgrading Fortuna.

## 7.2 First-launch account creation

Implement an internal Python service function such as:

```python
ensure_builtin_account()
```

This function should be called during embedded backend initialization, after the SQLite schema has been initialized or migrated.

It must:

1. Open the configured local SQLite database.
2. Check the dedicated metadata marker identifying the built-in account.
3. If the marker points to a valid existing account, reuse that account.
4. If no built-in account exists, generate a new UUID using Fortuna's existing UUIDv7 mechanism.
5. Create a `UserAccount` using the existing database/model layer.
6. Create the associated `UserSettings` using the existing initialization logic.
7. Generate a cryptographically random 32-byte password.
8. Encode it appropriately for the existing Argon2 password-hashing implementation.
9. Store only the password hash.
10. Immediately discard the plaintext password.
11. Persist the new user ID in the dedicated built-in account metadata marker.
12. Commit account creation, settings creation, and marker persistence atomically.

The operation must be transactional and idempotent.

Do not create duplicate built-in accounts during process crashes, repeated initialization, or application upgrades.

## 7.3 Internal creation, not HTTP registration

**Do not call the existing public HTTP registration endpoint to create the built-in account.**

Instead, reuse the internal database/model functionality that normal registration uses.

If needed, refactor common account-creation logic into an internal reusable function.

The correct division is:

```text
First launch:
Python internal initialization
    -> Account model/database layer
    -> SQLite creates persistent account

Normal application usage:
React
    -> Electron main
    -> Existing Python API
    -> Existing user-scoped business logic
```

Do not introduce a public "create built-in account" endpoint.

Do not make the built-in account creation mechanism remotely accessible.

## 7.4 Reserved username and account marker

Reserve:

```text
__fortuna_builtin__
```

for internal use.

However, do not use the username alone as the source of truth for identifying the built-in account.

Create dedicated database metadata that stores the built-in account's UUID.

For example, a metadata record could conceptually contain:

```text
key: builtin_account_id
value: <actual UUIDv7>
```

Adapt this to Fortuna's existing database architecture.

If an ordinary account already uses the reserved username, do not silently take control of it.

Handle the collision safely through explicit initialization failure or a deliberate, documented migration strategy.

Avoid breaking ordinary deployed installations that may already contain such a username.

## 7.5 Password behavior

The built-in account's password exists only to satisfy the account schema and preserve compatibility with the existing account model.

The user must never need it.

It must not be:

- A fixed default password.
- The same across installations.
- Printed in logs.
- Stored in plaintext.
- Exposed to React.
- Used by Electron for authentication.

Normal password login for the built-in account must be disabled where the built-in account is recognized as such.

Do not enable password modification for the built-in account.

# 8. Embedded authentication: security-critical

The embedded backend must never simply disable authentication.

It must authenticate requests originating from Electron main using a private per-launch secret.

## 8.1 Secret generation

Every time Electron launches the embedded backend:

1. Generate 256 bits of cryptographically secure random data.
2. Keep the secret in Electron main process memory.
3. Pass it privately to the Python process.
4. Never persist it to disk.
5. Never send it to React.
6. Never send it to a remote Fortuna server.
7. Never write it to logs.

Prefer an inherited private pipe or other controlled child-process communication channel.

An environment variable passed only to the child process may be used as a simpler initial implementation, provided it is documented as a security tradeoff and is not used as the runtime-mode selector.

The presence of this secret must not automatically enable embedded mode.

## 8.2 Request authentication

Electron main attaches the secret to requests destined for the embedded Python backend.

For example, use a dedicated internal authentication header.

Python validates the secret using a constant-time comparison.

After successful validation:

1. Load the persisted built-in account UUID.
2. Verify the account still exists.
3. Set the existing Flask request user context, such as `g.user_id`, to the built-in account UUID.
4. Execute the existing API endpoint with the same user-scoping rules used for ordinary authenticated users.

Conceptual example:

```python
if runtime_mode == "embedded":
    validate_embedded_secret(request)
    g.user_id = get_builtin_account_id()
else:
    authenticate_normal_fortuna_session(request)
```

This is illustrative; integrate it with Fortuna's actual decorators and authorization mechanisms.

In embedded mode, do not fall back to normal authentication when the private secret is absent or invalid.

A request without valid embedded authentication must not access the built-in user's data.

Apply authentication to all endpoints that expose or mutate private application data. Do not accidentally leave auxiliary endpoints unprotected.

## 8.3 Avoid ordinary expiring login sessions

The embedded backend should authenticate each request directly through its private per-launch secret.

Do not require the built-in account to perform ordinary password login.

Do not rely on the existing `TokenStore` session lifetime for embedded authentication.

An embedded application that remains open for days should not suddenly display a login page due to session expiration.

Normal remote sessions must retain their current behavior.

## 8.4 Account operation restrictions

In embedded mode, protect the built-in account from:

- Password-based login.
- Password modification.
- Account deletion.
- Ordinary user registration replacing the built-in identity.
- Unauthorized account identity changes.

Do not just hide buttons.

Enforce restrictions in Python.

Other existing data operations must continue to work using the built-in account ID.

For example:

- Reports.
- Accounts represented within Fortuna's business data.
- Categories.
- Metadata.
- Settings.
- Any other currently user-scoped resources.

## 8.5 Avoid server-deployment vulnerabilities

When Fortuna is launched as a normal deployed server:

- Do not create a built-in account automatically.
- Do not enable embedded authentication.
- Do not treat a desktop authentication header as valid authorization.
- Do not accept any HTTP request that changes runtime mode.
- Do not enable passwordless login.
- Keep existing normal `Fortuna-Auth` behavior.

The embedded authentication branch must not be reachable merely by changing frontend code, localStorage, an HTTP request header, or an ordinary server config file.

Even if the dedicated embedded executable is run accidentally on a remote machine, it must remain loopback-only and require its private secret.

Document the realistic threat model: this design prevents unauthenticated access through the localhost API, but it cannot guarantee protection against a fully compromised process running with the same operating-system user privileges.

# 10. API transport abstraction

Refactor `web/src/api.ts` to support two transports cleanly.

Do not mix remote authentication tokens with the embedded secret.

An external backend must never receive the embedded authentication secret.

If remote API requests are executed from Electron main, implement the necessary security controls there rather than relying on browser CORS behavior.

## 10.4 Connection and authentication isolation

Keep separate state for:

- Selected desktop mode.
- Selected remote backend URL.
- Remote authentication token.
- Built-in backend connection.
- Built-in authentication secret.

The built-in connection must never rely on the remote session token.

A remote token must be associated with its corresponding backend origin.

Switching remote backend URLs must not accidentally send credentials from the previous server to the new server.

Switching between Built-in and Remote must clear or invalidate stale frontend query caches and in-memory data views, without deleting persistent application data.

- Create the built-in account.

- Preserve it.
- Apply necessary migrations.
- Reuse the existing built-in account.
- Never replace it with a bundled sample database.

Migration failures must be reported without silently resetting or overwriting user data.

# 15. User-visible database controls

The user explicitly needs to locate the SQLite database file.

Add an action such as:

**Show Database in Explorer / Finder**

Use Electron's native shell APIs to reveal the actual file.

Also implement a safe backup/export function.

For example:

**Export Database Backup...**

Use Python SQLite's Online Backup API or an equivalent consistent backup procedure.

Do not copy only the `.sqlite3` file while the database may have pending WAL or journal data.

The exported backup should be a valid SQLite database.

Provide meaningful failure messages when export is unsuccessful.

If a database relocation feature is implemented, ensure the backend is stopped and paths are validated before moving data.

Do not silently change database locations between app versions.

# 16. Portable application support

The user wants an application that does not require global installation of dependencies.

Distinguish:

1. Self-contained installation.
2. Portable application distribution.
3. Portable user data.

Support the first in all distributions.

## 16.1 Windows portable ZIP

Provide a Windows x64 ZIP build containing the runnable Electron application.

Users should be able to extract and run it without:

- Running an installer.
- Administrator permissions.
- Python installation.
- Node.js installation.
- System service registration.

For the portable build, support a writable data directory beside the application:

```text
Fortuna/
├── Fortuna.exe
├── resources/
└── data/
    ├── fortuna.sqlite3
    └── ...
```

Use a reliable mechanism to distinguish portable mode from installed mode, such as a build-time flag or an explicit portable marker.

Do not automatically choose an unwritable installation directory.

If the application directory is not writable, show a clear error or offer a safe location selection. Do not silently lose data.

## 16.2 macOS application

Provide a self-contained native ARM64 `.app`.

Do not install Python globally.

Do not store mutable data inside the signed `.app` bundle.

Default to:

```text
~/Library/Application Support/Fortuna/
```

Optionally allow the user to select a separate writable database directory for portability.

Consider macOS app translocation, DMG read-only behavior, privacy permissions, and code-signing constraints.

Never depend on writing to the `.app` bundle.

## 16.3 Limitations of portability

Do not claim that an application leaves absolutely no operating-system traces.

Normal operating systems may retain:

- Execution history.
- Security metadata.
- Application caches.
- Logs.
- Recent application information.

The requirement is no globally installed development runtime or service, with application data stored in defined, discoverable locations.

# 17. Electron security

Configure production Electron windows with:

```javascript
nodeIntegration: false
contextIsolation: true
sandbox: true
```

Use a preload bridge for permitted functionality.

Serve the bundled React assets using a secure custom Electron application protocol where practical.

Do not run a production frontend development server.

Apply a restrictive Content Security Policy.

In particular, the renderer should not need direct networking access to the embedded backend if Electron main performs API requests.

Prevent:

- Arbitrary external navigation.
- Untrusted window creation.
- Remote code execution through renderer APIs.
- Unrestricted IPC invocation.
- Arbitrary filesystem access.
- Arbitrary backend request destinations.
- Exposure of the embedded secret.
- Accidental loading of remote executable scripts.

Validate IPC senders and arguments.

Keep the backend's authentication secret in Electron main, not in frontend state.

Do not treat loopback binding alone as authentication.

A Unix domain socket on macOS and a named pipe on Windows may be evaluated later, but localhost HTTP with strong authentication is acceptable for the initial implementation.

# 20. Testing requirements

Add automated tests wherever practical.

## 20.1 Normal server security

Verify:

- Existing server mode remains the default.
- Normal server startup does not create a built-in account.
- Normal server authentication still uses `Fortuna-Auth`.
- A forged desktop authentication header does not authenticate a normal server request.
- An ordinary config property cannot activate embedded mode.
- An HTTP request cannot activate embedded mode.
- Existing login, registration, logout, and authorization tests still pass.

## 20.2 Embedded runtime security

Verify:

- Embedded mode requires production environment.
- Embedded mode cannot run with debugging enabled.
- Embedded mode cannot bind to a public interface.
- Embedded mode cannot start without a valid private secret.
- Invalid or missing secrets cannot access protected data.
- Successful authentication resolves the correct built-in UUID.
- The embedded secret does not appear in logs or API responses.
- Normal username/password login cannot authenticate the built-in account.
- The built-in account cannot be deleted by ordinary account-deletion operations.

Verify:

- Fresh database creates exactly one built-in account.
- Username is `__fortuna_builtin__`.
- User ID is generated using UUIDv7.

- Plaintext password is not stored.
- The account ID marker is persisted.
- Repeated initialization creates no duplicates.
- Restarts preserve the same user ID.
- Upgrades preserve the account and associated data.
- Account settings are initialized correctly.
- Existing user-scoped APIs work with the built-in identity.
- Collisions with the reserved username are handled safely.

## 20.4 Electron startup

- Fresh Electron launch defaults to Built-in.
- The workspace opens without server configuration.
- The workspace opens without login.
- The embedded backend starts automatically.
- Backend port is dynamically assigned.
- Backend failures produce meaningful UI.
- Relaunch reuses the existing database.
- Closing the application cleans up the child process.

- Long-running application sessions do not require re-login.

- Remote to Built-in works.

# 26. Final acceptance criteria

The implementation is successful when all of these conditions are met.

### Scenario A — Fresh Windows 11 x64 installation

A user with no globally installed Python or Node.js environment opens Fortuna.

The application:

- Starts successfully.
- Initializes its bundled Python backend.
- Creates or reuses a local SQLite database.
- Creates or reuses the persistent built-in account.
- Opens the workspace immediately.
- Does not request a server address.
- Does not request a username or password.
- Allows reports and settings to be saved.
- Preserves data after restarting.

### Scenario B — Fresh macOS 26+ ARM64 installation

The same experience works using a native Apple Silicon Electron application with bundled Python.

No external runtime installation is required.

The database remains outside the signed application bundle.

### Scenario C — Switch to Remote

The Electron user opens Server settings, selects Remote, configures an existing Fortuna server, and logs in normally.

The application uses remote data and displays the normal logout control.

The local database remains unchanged.

### Scenario D — Return to Built-in

The Electron user selects Built-in from Server settings.

The application reconnects to the embedded backend and immediately resumes the same persistent local account without login.

The user's previous local data is intact.

### Scenario E — Existing web deployment

An existing web/server user continues using Fortuna as before.

The application still shows normal server configuration and account authentication.

Built-in mode is neither displayed nor available.

No desktop-specific authentication mechanism can be activated against an ordinary deployed server.

### Scenario F — Security verification

An unauthenticated local process cannot access the embedded backend's private data merely because it can connect to `127.0.0.1`.

An externally deployed Fortuna server never becomes an automatically authenticated single-user server through configuration changes or HTTP requests.

### Scenario G — Application update

The user upgrades Fortuna.

The application binaries may be replaced, but the SQLite database, built-in account UUID, account settings, reports, and other user data are preserved.

# 27. Non-negotiable constraints

**Do not break the existing web/server mode.**

**Do not globally install Python or Node.js on user computers.**

**Do not allow embedded mode to listen on external interfaces.**

**Do not allow unauthenticated access to the built-in account.**

**Do not use a fixed built-in password or hardcoded user ID.**

**Do not create the built-in account through the public registration HTTP endpoint.**

**Do not automatically enable embedded mode based on environment variables or HTTP requests.**

**Do not expose the embedded authentication secret to React or remote servers.**

**Do not put the live SQLite database inside application binaries or signed bundles.**

**Do not overwrite or reset user data during application updates.**

**Do not show built-in functionality in the normal web build.**

**Do not automatically synchronize local and remote data when switching modes.**

Implement the complete feature using the existing Fortuna architecture wherever possible. Security, backward compatibility, portability, and persistent user data are higher priorities than minimizing the number of changed files.
