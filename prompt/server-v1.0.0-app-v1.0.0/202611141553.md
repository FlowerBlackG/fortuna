Fortuna contains 3 parts: database, webpage, server.

database is only connected and edited by server. in fact, database itself is only a single sqlite3 file. without any encryption (we can think server is deployed in a trusted place).

server is used to provide account management and data management. 

webpage is used for user to operate and do data analysis.

webpage can transfer its data to server, and load data to server. but calculated data should be placed only in web itself, and re-calculate each time.

# Each parts introduction

texts like uuid and json should be stored in TEXT. time should be stored in TEXT as iso8601.
all floating point should be stored as REAL.


## database (we may also explain some design of python server here)

it just a sqlite3 file used by server.

tables:

### user_account

* user_id, use uuidv7, auto generated. store using TEXT. primary key
* username TEXT (defined and edited by user itself)
* create_time, iso8601, store in TEXT
* last_login_time, iso8601, TEXT
* user_password, TEXT. if user plain password is A (maybe A='abc123*'), the one stored in user_password should be protected by argon2id (python server can use argon2-cffi. webpage can just pass plaintext to python server since we assume web and server are protected by ssl. but you don't need to care anything about ssl ,we may later use nginx for it. you just forget about ssl things).

argon2's password hasher param (fix it in code, so if sometime we update lib version and lib changed default, we won't broke):

```
from argon2 import PasswordHasher, Type

ph = PasswordHasher(
    time_cost=3,
    memory_cost=65536,
    parallelism=4,
    hash_len=32,
    salt_len=16,
    encoding="utf-8",
    type=Type.ID,
)
```


### user_settings

this is used to store user-specific data like which is the default currency.

* user_id, uuid (primary key)
* settings, TEXT. store in json format. it is a json object, comes with key-value like:
```json
{
    "default_currency": "{UUID-OF-THAT-CURRENCY}"
}
```

user settings is edited in web app's user's setting page, the webpage should have the ability to correct it when found it malformed.

### currency

this is used to know user defined currencies.

* currency_id, uuid, TEXT (primary key)
* user_id, uuid, TEXT . remembers which user created it
* name, TEXT (like: CNY, USD, BTC) (of course can be duplicated. my CNY can be different meaning from other user's CNY).
* note, TEXT

### currency_exchange_rate

this is used to remember how user define their exchange rate.

* user_id, uuid, TEXT.
* numerator_currency_id, uuid, TEXT. 
* denominator_currency_id, uuid, TEXT.
* exchange_rate, REAL

user_id, numerator and denominator combined as the composite primary key.

for example, if numerator points to CNY, denominator points to USD, user might set the exchange_rate as like 6.7 

### institution

* user_id, TEXT (the user who created it)
* institution_id, uuid (primary key)
* name, TEXT (maybe like "东方财富", "binance", "招商银行")
* note, TEXT. this is used to hint user itself something. of course can be left blank.
for example, when name="中信证券", user might say note="港股通专用券商"

### asset_type

* user_id, TEXT (the user who created it)
* asset_type_id, uuid (primary key)
* name, TEXT
* color, TEXT (hex color code, contains exact 6 chars, all cap. like: 65AE73).
* note, TEXT. used to add some detail like: for name="上海交通卡", user might add note="交通联合卡，学校联名卡"
* custom_fields , TEXT , 
custom_fields actually stores a json array. each json object in the array like:
```json
{
    "display_order": an int. means the order when display on web. can be modified by user
    "data_order": an int. this value is used to know how to index real value from custom_fields_data . it should be expected start from 0, but when actually matching data (this should happen on website when it loaded user's data and assemble them), it should re-sort this json array according to data_order, then fetch data from custom_fields_data one by one. if any new fields added, display_order might change (which means new column stay before older is okay), but data_order should only be larger than any other data_order of this json array. should not be modified by user (but if it really modified by malformed api call which means user may be hacking, just let it hack).
    "type": a string, value is: "str" or "int" or "float" or "date". if date, corresponding data value should be iso8601 string.
    "field_name": string. like: "定期存款"
    "prefix": string
    "postfix": string
    "nullable": bool. if true, can set it as null in custom_fields_data. if false, webpage should let it has default value or prompt user to fill it. but, if user still submit malformed asset_custom_fields_data, our backend server can skip validate it, left it to webpage to handle it (or prompt user to correct it). this will only expected to happen when user using hacked illegal client, which only harm user itself, doesn't do any harm to our server or other user.
}
```

prefix and postfix are used like, for example interest rate, set postfix as "%" and when data is 5.5, webpage can show "5.5%"

we added custom fields so some asset type like fix deposit can be added fields like interest rate, due date, and when displaying with filter only selected this type, custom fields can show and used to filter again or sort.

### report

* user_id
* report_id , uuid, primary key
* title, TEXT. default to empty string "".
* create_time, iso8601
* update_time, iso8601

### report_record

* user_id
* report_id
* record_id , uuid, primary key
* currency_id (uuid points to currency table)
* asset_type_id (uuid points to asset_type entry)
* asset_custom_fields_data, TEXT. actually stores a json array. data can be decoded by the guidance of custom_fields. it can be empty array when custom_fields is empty array "[]".
* institution_id (uuid points to institution table entry)
* content, TEXT (this can duplicate, even in same report). this should be able to be multiline. in database line divider should be \n. if webpage need something like "<br/>", should be only converted lively on web app.
* amount, REAL
* effective_rate, REAL. defaults to 1. this value is used for, maybe if some asset need a fixed 1% fee when using it, i can set this to 0.99.  and maybe some asset is in fact some VIP card money, maybe $100 inside the card can always recharged by $70, i can also set the effective_rate to 0.7 so the calculation might be more accurate.

### system_info

this is used to store data about database and python server.

* fortuna_server_version_tag, TEXT. like "1.3.2"
* fortuna_server_version_code, integer.

above two fields are updated each time python server starts.

## webpage

webpage can be placed anywhere, maybe with that python server, maybe on other machines. we think, if placed elsewhere, it will prompt user to set where is the server's address, and saves inside some browser built-in storage (can be edited in web frontend's settings). if launched by python, python server can set its address somewhere so the webpage can itself detect the backend (call the ping api provided by server, if failed , prompt user the backend config page too).

webpage should be powered by react + react router + tdesign (by tencent). all router should be hash router since we may want to deploy it somewhere with only static web server.

---

when webpage logged in, server generates a token (not jwt, but our customized). the token looks like: {first 16 char of user_id}.{new generated uuidv7}.{a random hex integer from 100000 to FFFFFF}  . they are stored in backend server in a dict, key is this token , value is an object contains expiration datetime, user id.

webpage pass the token in header "Fortuna-Auth". like: curl xxx -H "Fortuna-Auth: xxx.xxx.FFFFFF". webpage should not decode it, just treat it as a whole identity identifier without any meaning.
server should first check whether the token exists in header, whether it exists in that token dict, whether it expired (configured in config.json)

---

webpage and server should communicate using our customized `IResponse` structure.
like:
```json
{
    "code": int (this should be http status code, indicating whether api good),
    "msg": str,
    "data": any (nullable, or int, float, str, object, array, all can)
}
```

note, in one response, there might be 2 http code, one is http itself's, one is in the IResponse. we separate them so, http's only tell whether the web connection is good. IResponse's one tell how api think.
which means, if server received one request, it should always response with http code as 200 (note, if logic before our server rejected, like client is using something like maybe rpc to call http api, which might be rejected by gateway, for these, even request really did reach server, http code can still be non-200, which make sense), but can set IResponse's code to different like 404 or 401 or 5xx or any. but for good api call, it set IResponse.code to 200 too.

both python side and typescript side, you should create the iresponse structure. for python side, also create static methods `IResponse.ok(optional data, optional msg)` and other handy tools.

typescript side, you should wrap axios to our own requests.
